Notification Handler --- Agent Development Instructions

1. Product Identity

Application name: Notification Handler

Purpose:

Build a focused mobile application that lets users define schedules for notifications from selected apps.

The primary Android use case is:

"Allow notifications from an app during a chosen time window and suppress them outside that window."

Example:

  • WhatsApp: allow 6:00 PM → 6:00 AM

  • Instagram: allow 10:00 AM → 10:00 PM

  • Gmail: always allow

The application should be simple, privacy-conscious, reliable, and focused specifically on notification scheduling.

2. CRITICAL PLATFORM FEASIBILITY REQUIREMENT

Before implementing the product, understand and respect this distinction.

Android

Android provides NotificationListenerService, which can receive notification events from the system and provides APIs such as cancelNotification(String key) / cancelNotifications(...).

Therefore, the core notification interception/suppression requirement is technically implementable on Android, subject to Android version, OEM behavior, user-granted Notification Access, and lifecycle/background restrictions.

Official reference:

https://developer.android.com/reference/android/service/notification/NotificationListenerService

iOS

Do NOT assume that iOS provides an equivalent API.

Apple's UNNotificationServiceExtension is for modifying notifications belonging to the app/remote notifications that are delivered to that app's extension. It is NOT a general-purpose notification listener for arbitrary third-party apps.

Therefore:

The Android and iOS products must not promise identical notification-control functionality.

The product architecture must explicitly model platform capabilities.

Required behavior

If a requested feature is not technically or officially supported on iOS:

  1. Do not fake the behavior.

  2. Do not claim that it works.

  3. Do not implement a fragile workaround that violates platform

    restrictions.

  4. Document the limitation.

  5. Provide the closest legitimate iOS functionality only if it is

    genuinely useful.

  6. Keep the Android implementation fully functional.

The agent must perform current platform/API verification before making platform-specific architectural decisions.

3. CODE-ONCE / MULTI-PLATFORM STRATEGY

The product should use a shared cross-platform architecture where practical.

Preferred approach:

Flutter + Dart for shared application code/UI/domain logic.

Flutter supports platform channels for calling native Android/iOS code.

Official reference:

https://docs.flutter.dev/platform-integration/platform-channels

Architecture:

                 Flutter / Dart
                      |
        +-------------+-------------+
        |             |             |
        v             v             v
       UI       Domain / Rules    Storage
        |             |             |
        +-------------+-------------+
                      |
                Platform Interface
                      |
          +-----------+-----------+
          |                       |
          v                       v
 Android Native              iOS Native
 Kotlin                       Swift
          |                       |
 NotificationListenerService   Supported iOS APIs only

Important

"One codebase" means:

  • Shared Flutter UI

  • Shared navigation

  • Shared data models

  • Shared schedule model

  • Shared schedule evaluation logic where possible

  • Shared persistence abstraction

  • Shared validation

  • Shared business rules

It does NOT mean:

  • One implementation of notification interception

  • One implementation of notification blocking

  • One native API for both platforms

Android-specific functionality must remain Android-native.

iOS-specific functionality must use only APIs legitimately exposed by Apple.

4. LANGUAGE / FRAMEWORK DECISION

The agent must evaluate the project before implementation and record the decision in docs/architecture-decision.md.

Preferred stack

Frontend/application layer - Flutter - Dart - Material 3, with a custom visual design system

Android native layer - Kotlin - Android SDK - NotificationListenerService - Android's official scheduling/background APIs where required

iOS native layer - Swift - Apple UserNotifications APIs only where applicable - Do not attempt arbitrary third-party notification interception

Why Flutter

Flutter is preferred because:

  1. The product has a substantial UI.

  2. We want Android and iOS packaging from one project.

  3. The domain model and schedule engine can be shared.

  4. Flutter provides platform channels for native capabilities.

  5. The native notification functionality is isolated behind a platform

    interface.

Do NOT choose Flutter merely because it avoids native code.

The project explicitly accepts native Kotlin/Swift code where platform functionality requires it.

Do not use Angular as the primary mobile UI

Angular is familiar to the product owner, but Angular + Capacitor introduces an additional native bridge layer without solving the fundamental platform API difference.

Use Flutter unless technical investigation proves another approach substantially better.

Do not choose React Native solely for cross-platform reasons.

Do not choose Kotlin Multiplatform solely because it can share code.

The deciding factor is reliable access to the required native notification APIs, not maximum theoretical code sharing.

27. TIME HANDLING

This is critical.

Use timezone-aware date/time handling.

Do not assume UTC for user schedules.

Schedules are based on the user's local device time.

Correctly handle:

  • Device timezone changes

  • Daylight-saving transitions where relevant

  • Midnight

  • Overnight schedules

  • Date boundaries

  • 12/24-hour display preferences

Store schedule semantics in a timezone-safe manner.

Do not compare formatted strings such as:

28. BACKGROUND / LIFECYCLE

Do not rely on the Flutter UI being open.

The Android notification listener must operate independently of the Flutter UI.

The native Android layer is responsible for receiving notification events.

The schedule data must remain available to the native notification service even when:

  • The Flutter app is closed

  • The activity is destroyed

  • The device screen is off

  • The user has not opened the app recently

Design the synchronization between Flutter storage and Android native service carefully.

If a chosen storage solution cannot be safely accessed from the native service, introduce a proper platform persistence layer rather than forcing an unsafe shortcut.
